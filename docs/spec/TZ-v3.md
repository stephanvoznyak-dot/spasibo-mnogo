## 1. НАЗНАЧЕНИЕ И ОБЛАСТЬ ПРИМЕНЕНИЯ

### 1.1. Назначение
Приложение предназначено для ведения личного криптографически защищённого журнала взаимных обязательств между участниками без использования центрального сервера, блокчейна и глобального консенсуса.

Система позволяет:
- создавать и восстанавливать криптографическую личность;
- фиксировать двусторонние обязательства (акты);
- обмениваться актами офлайн через QR-коды;
- выполнять автоматический многосторонний взаимозачёт (клиринг) по циклам;
- синхронизировать данные между экземплярами приложения по принципу роя.

### 1.2. Область применения
- Внутренний неттинг обязательств внутри организаций и групп;
- Локальные сообщества взаимного кредита;
- Офлайн-фиксация долговых обязательств;
- Пиринговые системы учёта без доверия к третьей стороне;
- Учебные и исследовательские прототипы децентрализованных расчётов.

### 1.3. Ограничения области применения
Приложение **не является**:
- платёжной системой;
- криптовалютным кошельком;
- средством эмиссии токенов;
- системой с принудительным исполнением обязательств.

## 3. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 3.1. Управление идентичностью

#### 3.1.1. Создание личности
1. При первом запуске приложение предлагает создать новую личность или восстановить существующую.
2. Генерация энтропии криптографически стойким ГСЧ (`crypto.getRandomValues`).
3. Формирование мнемонической фразы BIP-39 (поддержка 12 и 24 слов, русский и английский wordlist — приоритет английский для совместимости).
4. Отображение фразы пользователю с требованием подтверждения записи (пользователь должен ввести часть слов или подтвердить полный просмотр).
5. Деривация ключей (см. раздел 5.3.2).
6. Публичный ключ становится постоянным идентификатором агента.

#### 3.1.2. Восстановление личности
1. Пользователь вводит сид-фразу (по словам или целиком).
2. Нормализация ввода (lowercase, trim, единый разделитель).
3. Проверка контрольной суммы BIP-39.
4. Повторная деривация ключей.
5. При несовпадении контрольной суммы — отказ с понятным сообщением без утечки информации.

#### 3.1.3. Хранение секретов
- Приватный ключ **никогда** не экспортируется, не логируется и не передаётся.
- Сид-фраза хранится только в зашифрованном виде.
- HTML: IndexedDB / localStorage + опциональное шифрование паролем пользователя (AES-GCM через WebCrypto).
- APK: Capacitor Secure Storage / EncryptedSharedPreferences.
- Экспорт сид-фразы — только после двойного подтверждения и отображения предупреждений.

#### 3.1.4. Идентификатор агента
- Основной идентификатор: публичный ключ Ed25519 в формате hex (64 символа) или base64url.
- Короткий отпечаток (fingerprint): первые 8–12 символов hex + возможность показать полный ключ.
- Контакты сохраняются как пары `{fingerprint, fullPublicKey, displayName?}`.

### 3.2. Структура акта обязательства

| Поле        | Тип              | Описание                              | Изменяемость после M1 |
|-------------|------------------|---------------------------------------|-----------------------|
| `version`   | uint             | Версия формата акта (сейчас 1)        | Нет                   |
| `from`      | PublicKey        | Инициатор                             | Нет                   |
| `to`        | PublicKey        | Контрагент                            | Нет                   |
| `amount`    | positive integer | Сумма обязательства                   | Нет                   |
| `note`      | string           | Пометка (рекомендуемый лимит 280 символов) | Нет              |
| `timestamp` | uint64           | Unix-время создания (мс)              | Нет                   |
| `nonce`     | bytes (8–16)     | Случайное значение для уникальности   | Нет                   |
| `hash`      | bytes32          | SHA-256 канонической сериализации     | Пересчитывается       |
| `sigM1`     | Signature        | Подпись инициатора                    | Нет                   |
| `sigM2`     | Signature \| null| Подпись контрагента                   | Устанавливается один раз |

**Жёсткие правила валидации:**
- `amount` ∈ ℤ, `amount ≥ 1` (никаких float, никаких ≤ 0).
- После подписи M1 поля `from`, `to`, `amount`, `note`, `timestamp`, `nonce` считаются замороженными.
- Хеш **всегда** пересчитывается при проверке. Хранимое значение `hash` — кэш, а не источник истины.

### 3.3. Жизненный цикл акта (механика)

```
┌─────────────────────┐
│ 1. Черновик         │  Пользователь заполняет to, amount, note
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ 2. Подпись M1       │  Канонический CBOR → SHA-256 → Sign(sk_from)
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ 3. QR Stage 1       │  type: "act-proposal", payload = акт с sigM1
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ 4. Сканирование     │  Получатель проверяет sigM1 + пересчитывает hash
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ 5. Подпись M2       │  Получатель подписывает тот же hash своим sk
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ 6. Финализация      │  Акт записывается в журналы обеих сторон
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ 7. Клиринг          │  Проверка циклов и возможный взаимозачёт
└─────────────────────┘
```

### 3.4. Протокол обмена через QR

#### 3.4.1. Формат сообщения
Все QR-сообщения имеют единый конверт:

```json
{
  "proto": "normal-project",
  "ver": 1,
  "type": "act-proposal" | "act-final" | "sync-request" | "sync-response",
  "payload": "<base64url(CBOR)>"
}
```

#### 3.4.2. Типы сообщений
| type            | Назначение                              | Обязательные проверки          |
|-----------------|-----------------------------------------|--------------------------------|
| `act-proposal`  | Акт с подписью M1 (sigM2 = null)        | sigM1, hash, amount > 0        |
| `act-final`     | Полностью подписанный акт               | sigM1 + sigM2, hash            |
| `sync-request`  | Запрос отсутствующих актов (рой)        | —                              |
| `sync-response` | Передача запрошенных актов              | Подписи каждого акта           |

#### 3.4.3. Механика сканирования
1. Камера работает в непрерывном режиме.
2. При успешном декодировании QR выполняется валидация конверта и payload.
3. При ошибке подписи / хеша / суммы — понятное сообщение, акт не принимается.
4. Fallback: ручной ввод base64url или JSON (для отладки и крайних случаев).

### 3.5. Личный журнал (Ledger)

#### 3.5.1. Хранение
- Основное хранилище: **IndexedDB** (объектное хранилище `acts` + `meta`).
- Ключ записи: `hash` акта (или композитный ключ `timestamp + hash`).
- Индексы: `from`, `to`, `timestamp`, `status`.
- Резервное копирование: localStorage только для мелких настроек.

#### 3.5.2. Статусы акта
| Статус        | Описание                                      |
|---------------|-----------------------------------------------|
| `pending_m2`  | Ожидает подписи контрагента                   |
| `finalized`   | Подписан обеими сторонами, активен в графе    |
| `partially_cleared` | Частично погашен клирингом               |
| `cleared`     | Полностью погашен                             |
| `archived`    | Выведен из активного графа                    |

#### 3.5.3. Операции журнала
- `addAct(act)` — проверка подписей + хеша → запись.
- `getActs(filter)` — выборка по контрагенту, статусу, периоду.
- `verifyIntegrity()` — полная перепроверка всех актов при старте.
- `exportLedger()` / `importLedger()` — без приватных ключей.

### 3.6. Граф обязательств и клиринг (механика)

#### 3.6.1. Построение графа
```
V = множество агентов, встречающихся в финализированных актах
E = мультимножество рёбер (from → to, weight = remainingAmount)
```
`remainingAmount` = amount − уже клирингованная часть.

#### 3.6.2. Парный остаток
```
B_ij = Σ remaining(i→j) − Σ remaining(j→i)
```

#### 3.6.3. Алгоритм поиска циклов
Рекомендуемый подход — итеративный DFS с отслеживанием текущего пути:

1. Для каждой вершины запускается DFS.
2. При возврате в вершину, уже находящуюся в текущем пути, фиксируется цикл.
3. Циклы нормализуются (поворот к минимальному fingerprint) для устранения дубликатов.
4. Ограничение максимальной длины цикла (рекомендуется 8–12) для контроля производительности.

#### 3.6.4. Residual и сокращение
```
r(C) = min { remaining(e) | e ∈ C }

если r(C) > 0:
    для каждого e ∈ C:
        remaining(e) ← remaining(e) − r(C)
        если remaining(e) = 0 → удалить ребро / пометить акт как cleared
```

#### 3.6.5. Инварианты (обязательны к соблюдению)
1. ∀ i, j: B_ij после клиринга = B_ij до клиринга.
2. Суммарный вес всех рёбер не увеличивается.
3. Клиринг возможен только при r(C) > 0 и реальном цикле.
4. Фиктивный клиринг запрещён и должен возвращать явную ошибку.

#### 3.6.6. Стратегии клиринга
- **Ручной режим** (по умолчанию): показать циклы → пользователь подтверждает.
- **Автоматический режим**: клиринг всех положительных циклов с записью в журнал событий.

### 3.7. Рой (Swarm) — механика

#### 3.7.1. Цель
Синхронизация актов между экземплярами без центрального сервера.

#### 3.7.2. Модель сообщений (BitTorrent-inspired)
| Сообщение   | Назначение                                      |
|-------------|-------------------------------------------------|
| `bitfield`  | Битовая карта (или список hash) имеющихся актов |
| `have`      | Уведомление о появлении нового акта             |
| `want`      | Запрос конкретных hash                          |
| `piece`     | Передача одного или нескольких актов            |

#### 3.7.3. Транспорт в промышленном образце
- **HTML**: `BroadcastChannel` + события `storage` (в рамках одного origin).
- **APK**: абстрактный интерфейс `SwarmTransport` с заготовками под WebRTC / Nearby Connections.
- В текущей версии обязательна работа между вкладками одного браузера.

#### 3.7.4. Логика синхронизации
1. При появлении нового финализированного акта — рассылка `have`.
2. При получении `have` — проверка наличия → при отсутствии отправка `want`.
3. При получении `want` — отправка `piece` с полными актами.
4. Полученные акты проходят полную верификацию перед записью в журнал.

### 5.2. Криптография

| Назначение             | Библиотека / API                      | Примечание |
|------------------------|---------------------------------------|----------|
| Ed25519 подпись/проверка | `@noble/ed25519`                     | Аудит, малый размер, чистый JS |

**Запрещено:** Math.random для криптографии, любые самописные реализации Ed25519/SHA.

### 5.3. Деривация ключей (механика)

```
entropy (128 или 256 бит)
    ↓
BIP-39 mnemonic
    ↓
PBKDF2-HMAC-SHA512 (mnemonic + "mnemonic" + salt="", iterations=2048)
    ↓
seed (64 байта)
    ↓
Ed25519 keypair from seed[0..31]   // или стандартная деривация SLIP-0010 при необходимости
```

В промышленном образце допускается упрощённая схема (seed → напрямую keypair), но она должна быть явно задокументирована в PROTOCOL.md и быть детерминированной.

### 5.4. Сериализация

| Назначение                    | Решение              | Требование |
|-------------------------------|----------------------|----------|
| Каноническая сериализация акта| CBOR (cborg / cbor-x)| Детерминированный encode (canonical) |
| Хранение в IndexedDB          | Structured Clone / CBOR | — |
| QR payload                    | CBOR → base64url     | Минимальный размер |
| Экспорт журнала               | JSON (pretty) + CBOR | Человекочитаемый + компактный |

**Критично:** перед хешированием и подписью используется **один и тот же** канонический CBOR. Любое расхождение encode между сторонами делает подпись невалидной.

## 7. ДЕТАЛЬНАЯ МЕХАНИКА ОСНОВНЫХ СЦЕНАРИЕВ

### 7.1. Создание и подпись акта (M1)
1. Пользователь выбирает/вводит `to`, указывает `amount` и `note`.
2. Система генерирует `nonce` и `timestamp`.
3. Формируется объект акта без подписей.
4. Выполняется канонический CBOR encode значимых полей.
5. Считается SHA-256 → `hash`.
6. `sigM1 = Sign(sk_from, hash)`.
7. Акт сохраняется локально со статусом `pending_m2`.
8. Генерируется QR (`type: act-proposal`).

### 7.2. Приём предложения и подпись M2
1. Сканирование / ручной ввод.
2. Декодирование конверта и CBOR.
3. Пересчёт hash и проверка `sigM1`.
4. Проверка `amount ≥ 1`, совпадения `to` с текущим агентом (рекомендуется).
5. `sigM2 = Sign(sk_to, hash)`.
6. Акт переводится в статус `finalized` и записывается в журнал.
7. Запускается проверка клиринга.

### 7.3. Клиринг
1. Из всех `finalized` + `partially_cleared` актов строится граф по `remainingAmount`.
2. Запускается поиск циклов.
3. Для каждого цикла с `r(C) > 0` либо показывается UI, либо выполняется автоматическое сокращение.
4. Обновляются `remainingAmount` и статусы актов.
5. Событие клиринга фиксируется в журнале событий (опционально).

### 7.4. Синхронизация через рой
1. Новый финализированный акт → `have`.
2. Другой экземпляр получает `have` → если hash отсутствует → `want`.
3. Отправитель отвечает `piece`.
4. Получатель верифицирует и записывает акт.

## 10. МАТЕМАТИЧЕСКАЯ МОДЕЛЬ (справочно)

**Парный остаток:**
\[
B_{ij}(G) = \sum_{e:i\to j} w(e) - \sum_{e:j\to i} w(e)
\]

**Residual цикла:**
\[
r(C) = \min_{e \in C} w(e)
\]

**Операция клиринга:**
\[
w'(e) = 
\begin{cases}
w(e) - r(C) & e \in C \\
w(e) & e \notin C
\end{cases}
\]

**Инвариант:**
\[
\forall i,j \quad B_{ij}(\mathrm{Clear}(G,C)) = B_{ij}(G)
\]
