## 1. ОБЩЕЕ ОПИСАНИЕ ПРОДУКТА

Создай полностью автономное приложение **Normal Project / Personal Ledger** — децентрализованный личный журнал взаимных обязательств.

### Ключевые свойства
- Полностью офлайн после первой загрузки
- Криптографическая идентичность на основе BIP-39 + Ed25519
- Обмен обязательствами через QR-коды (камера)
- Автоматический многосторонний клиринг (взаимозачёт) по циклам
- Роевая архитектура обмена данными по принципу BitTorrent (bitfield / have / want / piece)
- Один HTML-файл ≈ 250–400 КБ
- Android-обёртка через Capacitor

**Важно:** Это промышленный образец. Код должен быть чистым, типизированным, хорошо структурированным, с обработкой ошибок, без «учебных» упрощений, которые снижают надёжность.

## 2. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 2.1. Идентичность
- Генерация и восстановление личности через мнемоническую фразу BIP-39 (12 или 24 слова)
- Деривация ключей: PBKDF2 → seed → Ed25519 keypair
- Приватный ключ **никогда** не покидает устройство
- Публичный ключ используется как идентификатор агента
- Хранение сид-фразы только в зашифрованном виде в localStorage (или secure storage в APK)
- Возможность экспорта/импорта сид-фразы (с предупреждениями)

### 2.2. Личный журнал (Ledger)
- Каждый пользователь ведёт **свой** личный журнал подписанных актов
- Это **не** блокчейн: нет блоков, майнинга, глобального консенсуса
- Каждый акт содержит:
  - from (публичный ключ)
  - to (публичный ключ)
  - amount (строго целое число > 0)
  - note (строка)
  - timestamp
  - hash (SHA-256 от канонической CBOR-сериализации)
  - sigM1 (подпись инициатора)
  - sigM2 (подпись контрагента)
- Акт становится финализированным только после двух подписей
- Журнал хранится локально, упорядочен по времени/порядку добавления
- Проверка целостности журнала при каждом запуске

### 2.3. Создание и обмен актами (QR)
Протокол обмена:

1. **Создание предложения (M1)**  
   Пользователь указывает контрагента (по публичному ключу или через предыдущий контакт), сумму и пометку.  
   Система сериализует акт в CBOR, считает хеш, подписывает приватным ключом инициатора.

2. **QR Stage 1**  
   Генерация QR-кода с подписанным предложением.  
   Получатель сканирует камерой.

3. **Подпись M2**  
   Получатель проверяет подпись M1, сумму и стороны.  
   Поля from/to/amount/note **заморожены**.  
   Получатель подписывает своей подписью.

4. **Финализация**  
   Полностью подписанный акт записывается в журналы обеих сторон.

5. **Клиринг**  
   После добавления акта система проверяет возможность взаимозачёта.

Требования к QR:
- Использовать компактную CBOR-сериализацию
- Поддержка больших QR (версия 10–20 при необходимости)
- Чёткое разделение стадий (предложение / финальный акт)
- Защита от XSS и подмены данных

### 2.4. Клиринг (Clearing)
- Автоматический поиск циклов в графе обязательств
- Расчёт residual (минимальный вес рёбер цикла)
- Сокращение весов рёбер цикла на величину residual
- Удаление рёбер с нулевым весом
- Клиринг **только** при реальном цикле и положительном остатке
- Запрет фиктивного клиринга
- Сохранение всех парных остатков (инвариант)
- Отображение пользователю: какие обязательства были взаимозачтены

### 2.5. Рой (Swarm) — BitTorrent-inspired
- Локальный обмен данными между вкладками/устройствами через BroadcastChannel (в браузере)
- Модель: bitfield / have / want / piece
- Возможность запрашивать отсутствующие акты у других экземпляров
- В APK — подготовка к будущему WebRTC/Wi-Fi Direct обмену (заложить интерфейсы)

### 2.6. Безопасность (обязательные требования)
Необходимо закрыть все ранее выявленные классы уязвимостей:

- XSS из пользовательских данных (сумма, note) → строгая санитизация + QR-схема
- Приём дробных и отрицательных сумм → только `integer > 0`
- Фиктивный клиринг → отказ при отсутствии цикла/остатка/актов
- Двойной клиринг одного ребра → клиринг строго по остатку
- Подмена hashHex → хеш всегда пересчитывается при verify
- Изменение суммы/сторон после M1 → поля заморожены
- Молчаливые ошибки записи → все ошибки записи журнала должны быть видимы пользователю

Дополнительно:
- Content Security Policy (для HTML)
- Защита от prototype pollution
- Безопасное хранение ключей
- Явные предупреждения при экспорте сид-фразы

## 3. ТЕХНИЧЕСКИЙ СТЕК

### HTML-версия (основная)
- Чистый TypeScript (строгий режим)
- Сборка в **один** HTML-файл (esbuild / vite singlefile / аналог)
- Криптография: WebCrypto + библиотека Ed25519 (noble-ed25519 или аналог)
- BIP-39: проверенная реализация
- CBOR: компактная библиотека
- QR: генерация и сканирование (jsQR / html5-qrcode / аналог)
- UI: современный, минималистичный, тёмная/светлая тема, адаптивный
- Хранение: localStorage + IndexedDB (для журнала при росте данных)
- Без внешних runtime-зависимостей после сборки

### Android APK
- Capacitor 6+
- WebView с доступом к камере
- Возможность использовать Secure Storage / EncryptedSharedPreferences для сид-фразы
- Правильные permissions (CAMERA)
- Сборка APK через Android Studio / Gradle
- Иконка, splash screen, название «Normal Project»

## 5. UI/UX ТРЕБОВАНИЯ

- Язык интерфейса: русский (основной) + возможность английского
- Первый запуск: онбординг с созданием/восстановлением сид-фразы
- Главный экран:
  - Текущий баланс обязательств (с кем сколько)
  - Кнопки: «Создать акт», «Сканировать QR», «Журнал», «Клиринг»
- Создание акта: выбор контакта / ввод публичного ключа, сумма, пометка
- Сканирование: полноэкранная камера + ручной ввод (fallback)
- Журнал: хронологический список с фильтрами и статусами (ожидает M2 / финализирован / клирингован)
- Экран клиринга: визуализация найденных циклов и результат взаимозачёта
- Настройки: экспорт/импорт, смена темы, информация о версии, предупреждения безопасности

Дизайн: строгий, технический, без лишней декоративности. Акцент на читаемость и безопасность.
