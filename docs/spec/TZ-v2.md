## 1. НАЗНАЧЕНИЕ И ОБЛАСТЬ ПРИМЕНЕНИЯ

### 1.1. Назначение
Приложение предназначено для ведения личного криптографически защищённого журнала взаимных обязательств между участниками без использования центрального сервера, блокчейна и глобального консенсуса.

Система позволяет:
- создавать и восстанавливать криптографическую личность;
- фиксировать двусторонние обязательства (акты);
- обмениваться актами офлайн через QR-коды;
- выполнять автоматический многосторонний взаимозачёт (клиринг) по циклам;
- синхронизировать данные между экземплярами приложения по принципу роя.

### 1.2. Область применения
- Внутренний неттинг обязательств внутри организаций и групп;
- Локальные сообщества взаимного кредита;
- Офлайн-фиксация долговых обязательств;
- Пиринговые системы учёта без доверия к третьей стороне;
- Учебные и исследовательские прототилы децентрализованных расчётов.

### 1.3. Ограничения области применения
Приложение **не является**:
- платёжной системой;
- криптовалютным кошельком;
- средством эмиссии токенов;
- системой с принудительным исполнением обязательств.

## 2. ТЕРМИНЫ И ОПРЕДЕЛЕНИЯ

| Термин              | Определение |

| **Акт**             | Двустороннее криптографически подписанное обязательство |
| **Журнал (Ledger)** | Упорядоченная локальная последовательность актов агента |

## 3. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 3.1. Управление идентичностью

#### 3.1.1. Создание личности
1. При первом запуске приложение предлагает создать новую личность или восстановить существующую.
2. Генерация энтропии криптографически стойким ГСЧ (WebCrypto `crypto.getRandomValues`).
3. Формирование мнемонической фразы BIP-39 (поддержка 12 и 24 слов).
4. Отображение фразы пользователю с требованием подтверждения записи.
5. Деривация:
   - PBKDF2-HMAC-SHA512 (2048 итераций или более) → seed;
   - из seed — ключевая пара Ed25519.
6. Публичный ключ становится постоянным идентификатором агента.

#### 3.1.2. Восстановление личности
1. Пользователь вводит сид-фразу.
2. Проверка контрольной суммы BIP-39.
3. Повторная деривация ключей.
4. При несовпадении контрольной суммы — отказ с понятным сообщением.

#### 3.1.3. Хранение
- Приватный ключ **никогда** не экспортируется и не передаётся.
- Сид-фраза хранится только в зашифрованном виде:
  - HTML: localStorage + дополнительное шифрование паролем пользователя (опционально);
  - APK: EncryptedSharedPreferences / Secure Storage Capacitor.
- Экспорт сид-фразы возможен только после явного подтверждения пользователем и отображения предупреждений.

#### 3.1.4. Идентификатор агента
В качестве идентификатора используется:
- полный публичный ключ (hex или base64), либо
- короткий отпечаток (fingerprint) с возможностью показать полный ключ.

### 3.2. Структура акта обязательства

Акт содержит следующие поля:

| Поле        | Тип              | Описание                              | Изменяемость после M1 |
|-------------|------------------|---------------------------------------|-----------------------|
| `version`   | uint             | Версия формата акта                   | Нет                   |
| `from`      | PublicKey        | Инициатор                             | Нет                   |
| `to`        | PublicKey        | Контрагент                            | Нет                   |
| `amount`    | positive integer | Сумма обязательства                   | Нет                   |
| `note`      | string           | Произвольная пометка (до 280 символов)| Нет                   |
| `timestamp` | uint64           | Unix-время создания (мс)              | Нет                   |
| `nonce`     | bytes            | Случайное значение для уникальности   | Нет                   |
| `hash`      | bytes32          | SHA-256 канонической сериализации     | Пересчитывается       |
| `sigM1`     | Signature        | Подпись инициатора                    | Нет                   |
| `sigM2`     | Signature \| null| Подпись контрагента                   | Устанавливается один раз |

**Правила:**
- `amount` ∈ ℤ > 0 (строго целое, без дробной части, без отрицательных значений).
- После формирования подписи M1 поля `from`, `to`, `amount`, `note`, `timestamp`, `nonce` считаются замороженными.
- Хеш всегда пересчитывается при проверке. Хранение готового `hash` служит только для удобства, источником истины является пересчёт.

### 3.3. Жизненный цикл акта

```
[Создание черновика]
        ↓
[Подпись M1 инициатором]
        ↓
[Передача через QR Stage 1]
        ↓
[Проверка M1 получателем]
        ↓
[Подпись M2]
        ↓
[Финализация → запись в оба журнала]
        ↓
[Проверка возможности клиринга]
```

### 3.4. Протокол обмена через QR

#### 3.4.1. Сообщения протокола
Все QR-сообщения имеют заголовок:
```
{
  "proto": "normal-project",
  "ver": 1,
  "type": "act-proposal" | "act-final" | "act-request" | ...,
  "payload": <CBOR или base64(CBOR)>
}
```

#### 3.4.2. Стадии
1. **act-proposal** — акт с подписью M1 (sigM2 = null).
2. **act-final** — полностью подписанный акт.
3. Допускается ручной ввод данных (fallback при невозможности сканирования).

#### 3.4.3. Требования к реализации QR
- Генерация: библиотека с поддержкой коррекции ошибок уровня M или Q.
- Сканирование: непрерывное сканирование с индикацией успеха/ошибки.
- Максимальный размер полезной нагрузки должен позволять передать полный акт.
- Защита от XSS: все данные из QR проходят строгую валидацию и санитизацию перед отображением.

### 3.5. Личный журнал (Ledger)

#### 3.5.1. Хранение
- Основное хранилище: IndexedDB (предпочтительно) или localStorage с версионированием.
- Каждый акт сохраняется только после успешной проверки подписей и хеша.
- Журнал упорядочен по `timestamp` + порядку добавления.

#### 3.5.2. Операции
- Добавление финализированного акта.
- Поиск актов по контрагенту, статусу, сумме, периоду.
- Проверка целостности всего журнала при запуске приложения.
- Экспорт журнала (без приватных ключей) в JSON/CBOR.
- Импорт журнала с проверкой подписей.

#### 3.5.3. Статусы акта в журнале
- `pending_m2` — ожидает подписи контрагента;
- `finalized` — подписан обеими сторонами;
- `cleared` — полностью или частично погашен клирингом;
- `archived` — выведен из активного графа.

### 3.6. Граф обязательств и клиринг

#### 3.6.1. Построение графа
Из множества финализированных и не полностью клирингованных актов строится ориентированный мультиграф:
- Вершины — агенты (публичные ключи);
- Ребро `from → to` с весом `amount` соответствует обязательству.

#### 3.6.2. Парный остаток
```
B_ij = Σ (веса рёбер i → j) − Σ (веса рёбер j → i)
```

#### 3.6.3. Поиск циклов
Реализуется алгоритм поиска простых циклов (DFS с отслеживанием пути или аналог).
Допускается ограничение максимальной длины цикла (например, 8–12) для производительности.

#### 3.6.4. Residual и сокращение
Для найденного цикла C:
```
r(C) = min { w(e) | e ∈ C }
```
Если r(C) > 0, веса всех рёбер цикла уменьшаются на r(C). Рёбра с нулевым весом удаляются.

#### 3.6.5. Инварианты клиринга
1. Все парные остатки B_ij сохраняются.
2. Общая сумма обязательств не увеличивается.
3. Клиринг выполняется только при наличии реального цикла и r(C) > 0.
4. Фиктивный клиринг (без актов / без цикла / без остатка) запрещён и должен возвращать ошибку.

#### 3.6.6. Пользовательский интерфейс клиринга
- Список найденных циклов с residual.
- Предпросмотр изменений остатков.
- Подтверждение пользователем (или автоматический режим с журналированием).
- Отображение результата: какие акты затронуты и на какие суммы.

### 3.7. Рой (Swarm)

#### 3.7.1. Назначение
Синхронизация актов между несколькими экземплярами приложения одного или разных агентов без центрального сервера.

#### 3.7.2. Модель
По мотивам BitTorrent:
- **bitfield** — битовая карта имеющихся актов (или их идентификаторов);
- **have** — уведомление о появлении нового акта;
- **want** — запрос отсутствующих актов;
- **piece** — передача конкретного акта.

#### 3.7.3. Транспорт (промышленный образец)
- HTML: `BroadcastChannel` + `localStorage` events (в рамках одного браузера).
- APK: заложить интерфейсы под будущий WebRTC / Wi-Fi Direct / Nearby Share.
- В текущей версии достаточно работы между вкладками одного браузера и подготовки абстракций.

### 3.8. Безопасность

#### 3.8.1. Обязательные меры
| ID   | Угроза                              | Требование к реализации                          |
|------|-------------------------------------|--------------------------------------------------|
| F01  | XSS из суммы / note                 | Санитизация + безопасный рендеринг + CSP         |
| F03  | Дробные / отрицательные суммы       | Валидация: только integer > 0                    |
| F04  | Фиктивный клиринг                   | Отказ при отсутствии цикла / остатка / актов     |
| F05  | Двойной клиринг одного ребра        | Клиринг строго по текущему остатку               |
| F06  | Подмена hash                        | Хеш всегда пересчитывается при verify            |
| F07  | Изменение полей после M1            | Поля заморожены после подписи M1                 |
| F08  | Молчаливые ошибки записи            | Все ошибки хранения отображаются пользователю    |

#### 3.8.2. Дополнительные требования
- Content-Security-Policy для HTML-версии.
- Защита от prototype pollution.
- Отсутствие `eval`, `Function`, небезопасного `innerHTML`.
- Приватные ключи не должны попадать в логи, исключения, QR, экспорты.
- Явные предупреждения при любом действии, связанном с сид-фразой.

## 10. МАТЕМАТИЧЕСКАЯ МОДЕЛЬ КЛИРИНГА (справочно)

Пусть G = (V, E) — ориентированный мультиграф обязательств.

Парный остаток:
```
B_ij(G) = Σ_{e: i→j} w(e) − Σ_{e: j→i} w(e)
```

Цикл C = (v₁ → v₂ → … → vₖ → v₁), k ≥ 3.

Residual:
```
r(C) = min_{e ∈ C} w(e)
```

Операция клиринга:
```
w'(e) = w(e) − r(C)   для e ∈ C
w'(e) = w(e)          для e ∉ C
```

Инвариант:
```
∀ i, j   B_ij(Clear(G, C)) = B_ij(G)
```
